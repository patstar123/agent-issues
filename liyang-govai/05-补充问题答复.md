# 补充问题答复：TeleAgent 排期、模型基线、接口协议、吞吐测算

> 新增背景（2026-08-12 补充）：
> - TeleAgent 是类似 Codex 的**通用桌面智能体**，工具调用、多模态、长任务能力已内置；
> - 目前为互联网产品，**支持自定义模型提供商（OpenAI 兼容 API + base URL）**；
> - 产品侧正在推进私有化部署，会考虑私有化场景下主模型、多模态模型、工具调用、长任务的**完整模型调用链**。

**这条补充信息大幅改善了项目的风险结构**：原先判定为最高风险的"TeleAgent 昇腾适配 vs 客户 NVIDIA 选型"冲突基本消解——只要能配置自定义模型提供商，TeleAgent 就不关心底层是 CUDA 还是昇腾，我们自建的 Qwen 服务即可作为其模型后端。风险从"**架构路线冲突**"降级为"**接口协议对齐 + 产品交付排期**"，前者可控，后者可规避。

## 问题一：TeleAgent 的私有化部署排期？

### 公开信息能确认的

| 时间 | 事件 | 来源 |
| --- | --- | --- |
| 2026-07-18 | WAIC 中国电信人工智能生态论坛正式发布 TeleAgent，产品对外全面开放、免费体验，内测用户超 30 万 | 中国电信官方、人民政协网 |
| 发布时口径 | 提供**公有云即时使用、私有化本地部署、属地专属运维**三类交付方案 | 人民政协网、国资委网站 |
| 发布时口径 | **企业版将于 Q3 推出**（"为企业提供更多的数字员工"） | 人民政协网 |
| 产品设计 | 内置 **Model Router（模型路由器）**，按 Query 自动分流到最合适的模型；6300+ Skills；四层安全防护（感知/推理/执行/记忆） | 多方报道 |

**公开渠道没有比"Q3 推出企业版"更细的排期**，也没有私有化版本号、私有化包发布时间、政务行业落地案例的公开信息。今天是 8 月 12 日，处于 Q3 中段。

### 我的判断

**月底拿到生产级 TeleAgent 私有化包并完成部署的概率低，不应作为月底交付的前提。** 三条理由：

1. **"企业版 Q3 推出"是集团层面的市场口径，不等于私有化包可交付到溧阳**。中间还隔着属地商务流程（江苏电信/常州分公司）、实施排期、许可发放。
2. **补充信息本身说明私有化方案仍在设计中**。"产品侧现在自己也在推进私有化部署，会考虑私有化场景下……完整的模型调用链"——"正在推进""会考虑"意味着私有化形态尚未定型，尤其是多模型调用链（主模型 + 多模态 + 工具调用 + 长任务）在私有化环境下如何编排、需要几个模型、各自资源占用多少，这些都还没有稳定答案。而这些恰恰是我们做卡位规划必须知道的。
3. **一个刚发布一个月的产品，其首批私有化交付必然伴随大量现场适配**。政务内网、离线激活、等保要求会集中暴露问题。

### 因此建议的策略

**把 TeleAgent 从"月底交付的前提"调整为"月底之后叠加的增强项"**，同时保留三条并行路径：

| 路径 | 内容 | 适用时机 |
| --- | --- | --- |
| **路径 1（推荐，保月底）** | 开源智能体栈（Dify / RAGFlow）+ 自建 Qwen3.6 服务，完成最小可用闭环与两个场景演示 | 立即可启动，不依赖任何第三方 |
| **路径 2（过渡，需合规确认）** | **TeleAgent 现有桌面客户端 + 自定义模型提供商指向内网 Qwen3.6 服务** | 若客户端可在政务网环境激活运行，这是最快获得完整智能体体验的方式，详见下方风险 |
| **路径 3（正式）** | TeleAgent 私有化包到位后，通过统一网关接入既有模型服务，平滑替换或与路径 1 并存 | 排期由电信侧决定 |

**路径 2 的价值与风险需要说清楚**：既然 TeleAgent 已支持自定义模型提供商，理论上可以让桌面客户端的模型调用全部指向内网自建服务，任务文件与数据留在本地——这与其宣传的"核心推理本地运行、敏感数据不出本机"设计一致。但必须先确认三件事：

- 客户端**是否需要联网做账号认证、许可校验或版本更新**？政务内网通常无互联网出口，若强依赖联网则此路不通；
- 客户端的**遥测与日志是否会外传**、能否关闭？这是政务合规审查的必查项；
- 自定义模型提供商配置的**覆盖范围**：是所有模型调用都走自定义端点，还是仅主对话模型走自定义、多模态/嵌入/工具编排仍回落到电信云端？**若存在回落，就等于数据出域，方案不成立。** 这一条最关键。

这三个问题已加入《04-待确认问题清单》。

## 问题二：Qwen3.6-35B-A3B 是否满足通用智能体主模型的基线？

### 结论

**作为起步基线够用，但不是"对标 Codex 体验"的水平；而且通用智能体恰好是这个模型的相对弱项——它的强项在编码类智能体。** 对溧阳的政务办公场景，我判断可以接受，但必须配合人在环路的设计，并且必须做真实任务集验证。

### 官方基准数据（Qwen3.6-35B-A3B 模型卡）

**编码类智能体——强项，全面超越上代**

| 基准 | Qwen3.6-35B-A3B | Qwen3.5-35B-A3B（上代） | Qwen3.5-27B（稠密） | Gemma4-31B |
| --- | --- | --- | --- | --- |
| SWE-bench Verified | **73.4** | 70.0 | 75.0 | 52.0 |
| SWE-bench Multilingual | **67.2** | 60.3 | 69.3 | 51.7 |
| Terminal-Bench 2.0 | **51.5** | 40.5 | 41.6 | 42.9 |
| Claw-Eval Avg | **68.7** | 65.4 | 64.3 | 48.5 |
| QwenWebBench (Elo) | **1397** | 978 | 1068 | 1197 |
| NL2Repo | **29.4** | 20.5 | 27.3 | 15.5 |

**通用智能体——相对弱项，多项指标低于上代或同代稠密模型**

| 基准 | Qwen3.6-35B-A3B | Qwen3.5-35B-A3B（上代） | Qwen3.5-27B（稠密） | 判读 |

**通用知识与中文能力——够用**：MMLU-Pro 85.2、MMLU-Redux 93.3、C-Eval 90.0、SuperGPQA 64.7、GPQA 86.0。
**多模态与文档——强**：MMMU 81.7、MathVista 86.4、RealWorldQA 85.3、**OmniDocBench 89.9**。

**与前沿闭源模型的差距要如实说明**：Terminal-Bench 2.0 上 GPT-5.6 Sol 为 91.9，Qwen3.6-35B-A3B 为 51.5。第三方综合评测（BenchLM）将其在"智能体工具使用与计算机任务"类别排在 133 个模型中的第 80 位。**如果客户的心理锚点是"Codex 那样的体验"，用这个模型会有落差，需要提前管理预期。**

### 对政务场景的适配性判断

关键在于：**政务办公类智能体任务与软件工程类智能体任务的难度结构不同。**

TeleAgent 在政务场景的典型任务是文案撰写、公文处理、深度调研、文档整理、表格处理、材料汇总——这类任务**链条短（3–10 步）、容错高（结果由人审核）、对领域知识依赖大于对推理深度依赖**。而 SWE-bench / Terminal-Bench 考的是 20–100 步的自主执行且中途不能出错。

一个简单的数学能说明长链条的风险：若单步工具调用成功率为 p，n 步任务的端到端成功率是 pⁿ。

| 单步成功率 | 5 步任务 | 10 步任务 | 20 步任务 |
| --- | --- | --- | --- |
| 95% | 77% | 60% | 36% |
| 90% | 59% | 35% | 12% |

Tool Decathlon 26.9 与 MCP-Atlas 62.8 说明该模型在多工具长链条上的单步可靠性并不高。**所以结论是：把智能体任务设计成短链条 + 人工确认节点，模型能力就够用；追求 20 步以上全自动，会失败。**

而这恰好与政务场景的内在要求一致——政务对"可控、可审计、可追溯"的要求本来就高于"全自动"，**人在环路在这里是特性而不是妥协**。这一点在向客户汇报时值得主动讲透，能把模型能力的客观局限转化为方案设计的合理选择。

### 落地建议

1. **主模型用 Qwen3.6-35B-A3B 起步**，开启 thinking 模式（`temperature=0.6, top_p=0.95, top_k=20`）+ `preserve_thinking`，官方明确说推理链保留对 agent 场景能提升决策一致性、减少冗余推理、改善 KV Cache 利用率；
2. **必须做真实任务集验证**：用客户真实的 20–30 个办公任务测端到端成功率，而不是看基准分数。这是唯一可信的判断依据；
3. **善用 TeleAgent 的 Model Router**：既然它内置按 Query 分流的能力，私有化时可配置分层——简单任务走 35B-A3B，复杂任务路由到更强模型。这需要与电信确认 Router 在私有化下能否配置多个自定义模型端点（已加入问题清单）；
4. **工具调用配置要正确**：vLLM 需 `--enable-auto-tool-choice --tool-call-parser qwen3_coder`，SGLang 需 `--tool-call-parser qwen3_coder`。配错会导致工具调用被当作纯文本返回，表现为"模型不会用工具"；
5. **如果验证后能力不足**，可选路径按优先级：① 优化 Skills 与工具设计、缩短链条、增加确认节点（成本最低、见效最快）；② 用 RAG 补足领域知识；③ 引入更大模型——但需注意 L20 单机跑不动 397B 级模型，这条路径受硬件限制；④ 混合云（敏感任务本地、复杂任务上云）——与"数据不出域"冲突，政务场景基本不可行。

**优先级 ①② 能解决绝大多数问题，这也是把预算投向知识库与场景工程而非更多算力的又一个理由。**

## 问题三：Qwen3.6-35B-A3B 是否满足 OpenAI 标准 API？是否支持 Responses 扩展协议？

### 先澄清一个概念

**模型本身不提供 API，API 由推理框架提供。** Qwen3.6-35B-A3B 是权重，OpenAI 兼容接口来自 vLLM / SGLang。所以这个问题应拆成"vLLM/SGLang 为该模型提供的接口能力"。这个区分很重要，因为它意味着接口能力可以通过升级框架版本来改善，不受模型限制。

### Chat Completions（`/v1/chat/completions`）：完全支持，推荐首选

| 能力 | 支持情况 | 所需配置 |
| --- | --- | --- |
| 基础对话、流式输出 | ✅ 完全支持 | 官方 OpenAI Python/JS SDK 直接可用 |
| **工具调用**（`tools` / `tool_choice` / `tool_calls`） | ✅ 支持 | vLLM：`--enable-auto-tool-choice --tool-call-parser qwen3_coder`；SGLang：`--tool-call-parser qwen3_coder` |
| **多模态输入**（图像、视频） | ✅ 原生支持 | 通过标准 `image_url` content part |
| 结构化输出 / JSON Schema | ✅ 支持 | vLLM structured outputs |
| **推理内容**（thinking） | ⚠️ 通过 `reasoning_content` 字段返回 | `--reasoning-parser qwen3`。**注意：`reasoning_content` 不是 OpenAI 标准字段** |
| 推理链保留（thinking preservation） | ⚠️ 需客户端配合 | `chat_template_kwargs: {"preserve_thinking": true}`，且客户端需回传历史推理内容 |

**这里有一个必须与 TeleAgent 对齐的细节**：thinking preservation 依赖客户端把上一轮的推理内容回传给模型。如果 TeleAgent 走 Chat Completions 且不认识 `reasoning_content` 这个非标准字段，那么推理链保留就用不上——按官方说法，这会降低 agent 场景的决策一致性，并因重复推理而**增加**总 token 消耗。对长任务场景影响不小，值得在对接时专门验证。

### Responses API（`/v1/responses`）：两个框架都已实现，但仍在成熟中

**vLLM**：已实现 `/v1/responses`、`/v1/responses/{id}`、`/v1/responses/{id}/cancel`。官方文档明确"与 OpenAI Responses API 兼容，可使用官方 OpenAI Python client"，支持 `input`、`instructions`、`tools`、`reasoning`、`background`、结构化输出、有状态会话。社区 issue 中有开发者表示**日常将 Codex CLI 指向自建 vLLM 使用**，0.20.1 修复了多轮语义的若干问题。

**SGLang**：同样已实现 `/v1/responses`。值得注意的是，其合并修复 PR（#25881）的验证环境正是 **`Qwen/Qwen3.6-27B-FP8` + `--reasoning-parser qwen3` + `--tool-call-parser qwen3_coder`**，覆盖了普通请求、function tool、多模态等场景，确认 function tool 能正确以 `ResponseFunctionToolCall` 返回而非泄漏为纯文本。**这是 Qwen3.6 系列 + Responses API + 工具调用可用的直接证据。**

**但两边都仍在快速修 bug，属于"可用但需锁版本、需实测"的状态**：

| 框架 | 已知问题 | 状态 |
| --- | --- | --- |
| vLLM | 多轮请求中 `reasoning` item 缺少 `content` 字段时 500 崩溃（langchain-openai 等客户端会这样构造） | Issue #34496，修复 PR 进行中 |
| vLLM | 多轮 `output_text` 缺 `id`/`status` 导致 SDK 校验失败；部分有状态路径依赖 harmony 格式，对非 harmony 模型支持待完善 | Issue #33089，0.20.1 已修复多项 |
| vLLM | 文档标注 Responses API "仅适用于文本生成模型" | 多模态在该端点下的支持需实测 |
| SGLang | array 格式 `input`、`input_text` 归一化、多模态崩溃、function tool 类型约束 | 已由 #25881 集中修复 |

### 结论与建议

1. **OpenAI 标准 API（Chat Completions）：完全满足**，含工具调用与多模态，这是成熟可靠的首选路径；
2. **Responses 扩展协议：vLLM 与 SGLang 均已支持**，且 SGLang 侧已用 Qwen3.6 验证过含工具调用的场景，但生态仍在收敛期；
3. **对接策略**：先与 TeleAgent 明确它调用哪个协议。若走 Chat Completions，直接可用；**若强依赖 Responses（Codex 类客户端常见），则需要锁定经过验证的 vLLM/SGLang 版本，并在 POC 阶段专项测试多轮 + reasoning item + 工具调用 + 多模态四个组合**，不要假定可用；
4. **不要用 latest 镜像**：Responses API 相关修复分散在多个版本，生产环境应锁定一个实测通过的版本号，并保留升级验证流程。

## 问题四：单机 8 卡 L20 预期能达到多少吞吐量？

### 测算依据（已用官方精确参数替换此前的估算）

Qwen3.6-35B-A3B 官方架构参数：

```
层数 40，Hidden 2048
层布局：10 × ( 3 × (Gated DeltaNet → MoE) + 1 × (Gated Attention → MoE) )
      → 标准注意力层仅 10 层，线性注意力层 30 层
Gated Attention：Q heads 16，KV heads 2，head_dim 256
Gated DeltaNet：V heads 32，QK heads 16，head_dim 128
MoE：256 专家（8 路由 + 1 共享），专家中间维度 512
词表 248320（padded）
```

由此得到精确的显存模型：

| 项 | 数值 | 推导 |
| --- | --- | --- |
| **KV Cache** | **20 KB / token**（BF16） | 每层 (2 KV heads × 256) × 2(K,V) × 2B = 2KB，× 10 个注意力层 |
| KV Cache（FP8） | 10 KB / token | 可用 `--kv-cache-dtype fp8` 换取一倍容量 |
| DeltaNet 递归状态 | 约 31 MB / 序列（**与上下文长度无关**） | 30 层 × 32 heads × 128 × 128 × 2B |
| 权重（FP8 驻留） | 约 38–40 GB | 专家约 32.2GB + 非专家约 6GB + 词表嵌入约 2GB（BF16）+ 视觉编码器 |

**这个 KV Cache 数字是本模型最大的优势**：得益于 3/4 的层使用线性注意力，20KB/token 只有同规模全注意力模型的约四分之一。128K 上下文每请求仅约 2.6GB。

### 配置权衡（这是对原方案的重要修正）

官方明确建议：**上下文至少保持 128K 以保留 thinking 能力**（默认 262K）。智能体长任务会累积大量上下文（工具返回结果 + 推理链保留），32K 远不够用。这与政务问答追求高并发短上下文的目标存在冲突，需要在卡位编排上区别对待。

| 配置 | KV 池 | 8K 上下文 | 32K | 128K | 262K | 通信开销 |
| --- | --- | --- | --- | --- | --- | --- |
| TP=2（96GB/副本）× 4 副本 | 约 48GB/副本 | 245/副本 · **980 总** | 70 · **280** | 18 · **72** | 9 · **36** | 最低 |
| **TP=4（192GB/副本）× 2 副本** | 约 140GB/副本 | 712 · **1424** | 204 · **408** | 52 · **104** | 26 · **52** | 中等 |
| TP=8（384GB）× 1 副本 | 约 324GB | **1650** | **473** | **122** | **61** | 最高 |

（并发数 = KV 池 ÷（上下文 × 20KB + 31MB 状态），为显存上限，实际还受吞吐约束）

### 吞吐测算

**解码是显存带宽受限**，且 MoE 的专家覆盖率随批次上升（256 专家、每 token 激活 9 个）：

| 批次 | 激活专家占比 | 每 step 需读权重 | TP=2 每卡 | 理论 step/s | 调优后实测预估（55%） |
| --- | --- | --- | --- | --- | --- |
| 8 | 22% | 13.1 GB | 6.6 GB | 131 | — |
| 32 | 63% | 26.4 GB | 13.2 GB | 65 | 36 step/s |
| 64 | 87% | 34.0 GB | 17.0 GB | 51 | 28 step/s |
| 128 | 98% | 37.6 GB | 18.8 GB | 46 | 25 step/s |

**单机 8 卡聚合能力预估**：

| 指标 | 预估值 | 说明 |
| --- | --- | --- |
| **聚合输出吞吐** | **4,000–6,000 tok/s** | 4 副本 TP=2，批次 64/副本，已按 7 折扣除 prefill 竞争与长上下文开销 |
| **单流输出速率**（低负载） | 60–120 tok/s | 远超阅读速度 |
| **单流输出速率**（高负载） | 20–28 tok/s | 恰为流畅阅读速度 |
| **Prefill 吞吐** | 40,000–50,000 tok/s | FP8 有效算力约 570 TFLOPS（MFU 30%）÷ 6 GFLOPs/token，再打 5 折 |
| **文档解析** | 20–50 页/秒（A4 扫描页） | 按 1000–2000 视觉 token/页 |
| **政务问答类并发**（8K 上下文，非 thinking） | **80–150 路同时生成** | 受吞吐约束而非显存 |
| **智能体长任务并发**（64–128K 累积上下文，thinking + 工具调用） | **20–40 个任务同时运行** | 见下方说明 |

**智能体并发要单独看，这是与问答场景的本质区别**：一个 Codex 类任务会持续数分钟到数十分钟，累积上下文 50–200K，输出（含推理链）可达数万 token。按单任务总输出 20K token、聚合 4000 tok/s 估算，系统每小时可完成约 700 个任务；若单任务平均耗时 5 分钟（其中含工具执行的 GPU 空闲时间），则**同时在跑约 20–40 个任务**。对溧阳各委办局的规模，这个量级是充裕的。

### 三个能显著改变实测结果的工程要点

这几项在报告和常规方案里都不会出现，但对 L20 这类非主流卡影响很大：

1. **必须做 MoE kernel 调优，否则性能显著下降**。vLLM 官方明确要求用 `benchmark_moe.py` 为具体硬件生成调优配置（本模型对应 `E=256,N=512,device_name=NVIDIA_L20.json`），再通过 `VLLM_TUNED_CONFIG_FOLDER` 加载。L20 不是主流卡，几乎必然没有预置配置，**这一步是 POC 必做项**，跳过会让上面所有测算失效。
2. **MTP（多 token 预测）可提升解码速度**，官方支持 `--speculative-config '{"method":"qwen3_next_mtp","num_speculative_tokens":2}'`。低并发时收益明显（约 1.4–1.6 倍），高并发时因算力被占用收益递减，社区亦有配置不当导致延迟劣化的报告。**建议实测后按时段启用**：低峰期开启改善单流体验，高峰期关闭保吞吐。
3. **Ada 架构用不上部分新 kernel**。FlashInfer TRTLLM MoE FP8 kernel 需要 SM100（Blackwell），DeepGEMM 需要 SM90+，L20 是 SM89，只能走 Triton/Marlin 路径——这也是为什么第 1 点的手工调优不可跳过。好消息是 Ada 原生支持 FP8 Tensor Core，FP8 权重本身可以正常跑。

另外，`--language-model-only` 可跳过视觉编码器与多模态 profiling，为纯文本副本释放额外 KV 空间，适合专门服务政务问答的副本。

### 推荐编排（替代原方案的静态分配）

考虑到智能体长上下文与问答高并发的冲突，建议按负载类型分区：

| GPU | 配置 | 服务对象 | 容量 |
| --- | --- | --- | --- |
| 0–3 | TP=4，`--max-model-len 131072`，含视觉 | **TeleAgent 智能体长任务 + 多模态文档解析** | 128K 上下文约 52 路；64K 约 104 路 |
| 4–5 | TP=2，`--max-model-len 32768`，`--language-model-only` | 政务问答、公文写作（高并发短上下文） | 32K 约 70 路；8K 约 245 路 |
| 6 | 辅助模型池 | Embedding + Rerank + 内容安全 + ASR | 合计 < 12GB |
| 7 | 弹性 | 开发 / LoRA 微调 / 压测；高峰时与 GPU 6 组成第二个问答副本 | — |

夜间与非高峰时段可将 GPU 4–7 整体转为批处理（文档批量解析、知识库重建索引、微调），实现分时复用。

**所有数值均为基于官方架构参数的理论测算，最终必须以 MoE 调优后的实测压测为基线。** 建议压测用 `vllm bench serve`，分 8K/32K/128K 三档上下文、多个并发档位各跑 5 轮取中位数。
