# 溧阳市政务 AI 算力本地化项目 — 客户需求分析

> 输入材料：《溧阳市算力本地化部署建议报告》（溧阳市数据局，2026 年 8 月）
> 补充口径：通用智能体考虑中国电信 TeleAgent；本月底完成私有化；硬件暂定 NVIDIA L20
> 文档状态：售前需求分析稿，用于内部对齐与客户沟通，结论待《04-待确认问题清单》回填后定稿

---

## 一、一句话理解客户

客户（溧阳市数据局）真正要买的不是 GPU，而是**"一个能让全市各委办局在本月底就用上、且数据不出域的政务智能体底座"**。
报告通篇在论证"为什么要本地化"和"买什么卡"，但项目的成败其实取决于报告里几乎没写的三件事：**智能体平台从哪来（TeleAgent 私有化）、知识从哪来（RAG 语料与知识库）、谁来运维（专家小组 7 人皆为兼职）**。

因此本项目应被理解为一个 **"算力 + 平台 + 应用"三段式交付项目**，而非单纯的硬件采购项目。报告当前 200 万预算 100% 分配给硬件，是本项目最需要在方案阶段纠正的结构性问题。

## 二、客户决策链与关键人

报告附件《溧阳市政务领域人工智能运用研究小组（建议稿）》实际上是一份高价值的决策链地图：

| 角色定位 | 单位 / 人员 | 对本项目的意义 |
| --- | --- | --- |
| 业务决策与组织协调 | 数据局 黄黎明（副局长） | 项目发起人，"熟练运用各类大模型"，对效果有直观判断力，不易被参数话术说服 |
| 技术对口与方案把关 | 数据局 谢谦尧（规划协调股股长） | 描述为"擅长各类智能体应用、开发部署"，是方案技术评审的实际对手方，需给到可验证的细节 |
| 场景需求方（合规/审查） | 纪委监委 陆晨 | 有 agent 工具开发经验，倾向自建小应用；场景涉密等级最高 |
| 场景需求方（公文） | 市委办 王煜 | 公文写作/审核场景的最终用户，对生成质量要求最严 |
| 场景需求方（公安） | 公安局 葛子斌、管省超 | 全栈开发 + SQL 优化能力，会自建应用；公安网与政务网隔离，需单独讨论 |
| 本地技术承接方 | 溧投数科 吉竹庆 | 精通 RAG、Prompt、Agent，具备分布式训练与边缘推理经验，是本地化运维与二次开发的实际落地人 |

**判断**：这是一支"有动手能力、但缺统一底座"的队伍。7 人中至少 4 人能自己写应用。这决定了方案取向——
- 客户不需要我们包办每一个应用，**需要的是一个开放的、带 API 和开发环境的平台**；
- 客户会自己做验证测试，**任何夸大的并发/性能承诺都会在验收时被打回**；
- 溧投数科是必须拉进来的合作方，也是项目交付后的运维接口人。

## 三、需求分层拆解

### 3.1 硬件算力需求

**客户已明确的（显性需求）**

| 维度 | 客户要求 | 出处 |
| --- | --- | --- |
| 形态 | 8 卡 PCIe 形态 GPU 服务器，独立整机承载 | 报告三(二)、三(三) |
| GPU 型号 | NVIDIA L20 48GB（已完成 4 厂商横向对比后定型） | 报告三(二) |
| 单机显存 | **≥ 256GB**（明确写为"必须"） | 报告三(一) |
| 参数覆盖 | 7B–122B 参数规模的开发与推理 | 报告三(一)、三(三) |
| 存储 | 服务器本地盘承载，一二期均不建独立存储集群 | 报告三(三) |
| 分布式 | 预留多机集群组建能力 | 报告三(一) |
| 零散算力 | 用边缘智算终端补充，分配给个人使用 | 报告三(三) |
| 建设节奏 | 分两期，一期先测试开发、二期扩容 | 报告三(三) |
| 总预算 | 200 万（一期 91 万 / 二期 109 万） | 报告三(四) |

**客户没写但必然存在的（隐性需求，需在方案中主动补齐）**

1. **机房承载条件**。8 卡 L20 服务器配 4×2000W 电源，满载实测功耗约 3.5–4.5kW（8×350W GPU + 2 颗海光 7470 + 1TB 内存 + 高转速风扇）。加上 UPS 与制冷冗余，需**单机柜 ≥ 6kW 配电与等量制冷**。政务机房常见配置为 4–6kW/柜，属于**一期落地的潜在阻塞项**，报告完全未涉及。同时 8 卡被动散热卡依赖服务器高转速风扇，噪音在 70dB 以上，不可置于办公区。
2. **一期的网络接入**。交换机被排在二期（10 万），但一期就有 1 台 GPU 服务器 + 4 台边缘终端需要接入政务网。GPU 服务器只有 2×25G 光口，边缘终端只有 10GbE RJ45 + QSFP。**一期必须依赖现有网络资源，需现场核实端口类型与可用数量**，否则设备到货即无法联网。
3. **共享存储**。两台服务器各自用本地盘，意味着模型权重要存两份、向量索引无高可用、审计日志分散。等保对日志留存有集中化要求。**至少需要一套 NAS 或以通用服务器搭 MinIO/NFS**。
4. **离线权重导入通道**。若政务内网无互联网出口，Qwen3.6-35B-A3B-FP8 权重约 35GB+，加上 Embedding/Rerank/OCR/ASR 模型，首次导入总量 60–100GB，需明确摆渡方式与安全审批流程。
5. **国产 CPU + NVIDIA GPU 的适配验证**。配置为"海光 7470 + 8×L20"，属信创合规下的混合组合。需验证 NVIDIA 驱动与 CUDA 在海光平台的兼容性、IOMMU/ACS 设置、PCIe 拓扑（是否经 PCIe Switch）与 NCCL P2P 实测带宽。这是**必须在 POC 阶段验证、不能想当然**的一项。
6. **备件与维保**。8 卡整机的单卡故障会导致整机降级。需 3 年原厂维保 + GPU 备件承诺，报告未列此项费用。

**技术判断（详细推导见《03-原报告技术校核与勘误》）**

- L20 的三条硬约束报告未提及，但直接决定架构：**① 无 NVLink**（多卡只能走 PCIe Gen4 x16，约 32GB/s 双向）；**② 不支持 MIG**（只能用 vGPU 授权或时间片，无法硬切分）；**③ 不支持 FP4**（Ada 架构无 FP4 张量核）。
- **单机 8 卡 = 384GB 显存**，满足客户"≥256GB"要求，且有余量。
- **二期两台服务器之间无法做跨机张量并行**：2×25G 网络（无 RDMA 明确要求）与跨机 TP 所需的 100G+ RoCE/IB 相差一个数量级。二期扩容的正确定位是**"增加模型服务副本 + 冗余"，而不是"合并算力跑更大模型"**。报告"预留多机集群"的表述需要收敛为此含义，否则二期验收时会出现预期落差。

### 3.2 模型选型需求

**客户已明确的**

报告三(一)已经自主完成选型，指定 **`Qwen/Qwen3.6-35B-A3B-FP8`** 作为多模态主力模型，并准确描述了其特征（35B 总参 / 约 3B 激活、稀疏 MoE、256 专家、原生视觉编码器、混合架构、原生 262K 可扩 1M、Thinking/Non-Thinking 双模式、推理链保留）。

**经核实，客户的这一选型是正确且相当专业的**（Qwen3.6-35B-A3B 于 2026-04-16 开源，Apache 2.0 可商用）。其关键特性对本项目高度适配：

| 模型特性 | 对项目的价值 |
| --- | --- |
| MoE 35B / 激活 3B | 解码时只读约 3B 权重，L20 的 864GB/s 带宽足以支撑高吞吐，**是"用推理卡跑出高并发"的关键** |
| Gated DeltaNet 混合架构（约 3/4 层为 O(n) 线性注意力） | KV Cache 占用仅为同规模全注意力模型的约 1/4，**长上下文并发能力被大幅放大** |
| 原生多模态（文本+图像+视频） | 一个模型即覆盖政务问答、公文、扫描件/截图解析，**无需再为多模态单独配 122B 模型** |
| OmniDocBench 89.9 | 文档版面解析能力强，直击"多模态政务文档处理"场景 |
| SWE-bench Verified 73.4 | 智能体编码能力强，直接服务专家小组的自建应用开发需求 |
| Apache 2.0 | 无授权成本与合规风险，符合自主可控诉求 |
| 官方支持 vLLM / SGLang，OpenAI 兼容 API | 可被 TeleAgent 或任意智能体平台以标准接口接入 |

**需要修正的选型逻辑**

报告存在一处**内在矛盾**：需求分析中写"多模态政务智能体（视觉+语言，122B 模型起）"并据此推导"4–8 张 GPU"，但同一段落最终选定的是 35B-A3B。这导致后续容量测算（"8 卡服务器部署 1 个 122B 模型实例，并发 2–4 个"）是按 **122B 稠密模型**算的，而实际要部署的是 **35B-A3B 稀疏模型**，两者对显存与带宽的需求相差 5–10 倍。这是报告并发数严重低估的根源。

**客户没写但必然需要的模型（隐性需求）**

报告只提了一个对话主模型，但任何可用的政务 AI 平台至少还需要 5 类模型，全部缺失：

| 缺失能力 | 没有它会怎样 | 资源占用 |
| --- | --- | --- |
| Embedding（向量化） | **无法做 RAG**，智能体只能靠通用知识胡编，政务问答直接不可用 | 小，可与他模型共卡 |
| Rerank（重排） | RAG 召回准确率显著下降，政策法规类问答会张冠李戴 | 小，可共卡 |
| OCR / 版面解析 | 存量政务文件多为扫描 PDF 与红头文件影印件，无法入库 | 中等，或用主模型视觉能力 |
| ASR（语音识别） | 会议记录、12345 热线录音场景无法开展 | 小 |
| 内容安全审核 | **政务场景生成内容无合规过滤，是不可接受的政治风险** | 小，或用规则+小模型 |

**微调需求需要收敛预期**。报告在开篇提出要支撑"大模型微调训练"，但 L20 是推理定位卡（Ada 架构、GDDR6、无 NVLink）。客观能力边界为：
- 可做：7B–14B 稠密模型全参微调；≤35B 模型 LoRA / QLoRA 微调；
- 不建议做：35B MoE 全参微调（优化器状态需 400GB+，需 ZeRO-3 + CPU offload，速度不可接受）；任何 70B+ 训练。
- 方案中应明确表述为**"轻量微调（LoRA）+ 推理为主"**，避免验收时对"训练"能力产生争议。实际上政务场景 90% 的效果提升来自 RAG 与提示工程，而非微调，这一点需要向客户讲清楚。

### 3.3 智能体平台需求（本次补充口径的核心）

**客户倾向：中国电信 TeleAgent（星辰超级智能体）**

已核实的产品事实（2026 年 7 月 18 日 WAIC 中国电信人工智能生态论坛发布，中电信人工智能科技有限公司出品）：

| 维度 | 事实 | 对本项目的含义 |
| --- | --- | --- |
| 定位 | 中国电信首款 AI 原生应用，"数字员工 → 数字团队" | 与客户"各委办局用得上的通用智能体"诉求高度契合 |
| 能力 | 内置 6300+ Skills，覆盖文案撰写、代码编写、深度调研、运维支持、创意速构、任务自动执行；支持任务自动规划、长时间运行与批量任务 | 开箱即用能力远超自建，能直接支撑"月底可演示" |
| 安全 | 围绕"感知、推理、执行、记忆"四层安全防护，可信可控可审计贯穿全生命周期；核心推理本地运行、敏感数据不出本机 | 与政务等保诉求同频，是相对开源栈的最大优势 |
| 交付形态 | 提供公有云即时使用、**私有化本地部署**、属地专属运维三类方案，支持在企业内网完成大模型与智能体全栈部署 | 私有化路径官方明确支持 |
| 产品形态 | **类似 Codex 的通用桌面智能体**，工具调用、多模态、长任务能力已内置；目前为互联网产品 | 无需我方自建智能体核心能力，价值在于集成 |
| **模型接入** | **支持自定义模型提供商（OpenAI 兼容 API + base URL）**；内置 Model Router 按 Query 自动分流到最合适的模型 | **✅ 关键利好：平台对底层算力无感，我方在 L20 上的自建服务可直接作为其模型后端，原"昇腾 vs NVIDIA"冲突消解，L20 选型得以保留** |
| 底座 | 依托全栈自研星辰大模型搭配其他模型 | 需确认私有化版是否**必须**搭配星辰模型，或可完全用自定义模型替代 |
| 算力适配 | "联合华为昇腾完成底层算力适配"，国产智算底座 | 仅表明其已验证的算力路线，因支持自定义模型端点而不构成架构约束；仅需确认**平台自身组件**是否强制昇腾环境 |
| 成熟度与排期 | 内测用户超 30 万；**企业版 Q3 推出**；产品侧正在推进私有化部署，会考虑私有化下主模型、多模态、工具调用、长任务的完整模型调用链 | **⚠ 当前最大风险：私有化方案仍在设计中，月底拿到生产级私有化包的概率低**（分析见《05》问题一） |

**由此形成四个必须前置解决的问题**（详见《04-待确认问题清单》第一节，完整分析见《05》问题一）：

1. **私有化包的排期与当前阶段？** 公开口径仅"企业版 Q3 推出"。判断是月底赶不上，因此不应作为月底交付的前提。
2. **自定义模型端点的覆盖范围？** 是所有模型调用都走自定义端点，还是仅主对话模型走自定义、而多模态/嵌入/工具编排仍回落电信云端？**若存在回落即等于数据出域，政务场景一票否决。这是整份清单最关键的一问。**
3. **私有化最小部署资源清单是什么？** 平台自身（Model Router、任务编排、沙箱执行环境、记忆库、向量库）会占用相当的 CPU/内存/存储，甚至独立 GPU。若未预留，会挤占模型推理的 8 张卡。
4. **授权与许可机制**。按用户数还是并发计费、Skills 是否全量（哪些依赖外网因而在内网失效）、**能否在完全无外网环境离线激活与离线升级**——政务内网无法回连许可服务器，这是私有化项目的经典翻车点。

**仍须准备开源备选栈**。鉴于 ① 私有化排期不确定、② 产品刚发布一个月、首批私有化交付必然伴随大量现场适配、③ 月底的硬性时限，方案必须包含一条不依赖第三方交付节奏的路径（Dify / RAGFlow / n8n + 自建 Qwen3.6 服务），以保证"月底有东西可演示"这一政治目标不落空。此外还有一条过渡路径值得评估：**TeleAgent 现有桌面客户端 + 自定义模型端点指向内网服务**，但需先排除客户端联网依赖、遥测外传、云端回落三个合规障碍（《04》1.1b）。

### 3.4 应用与场景需求

**报告明确列出的 4 类场景**

| 场景 | 报告给的模型规格 | 修正后的建议 | 关键难点（报告未提） |
| --- | --- | --- | --- |
| 政务问答智能体 | 7B–14B，单卡 ≥24GB | 统一用 35B-A3B，效果远超 14B 且成本相近 | **准确率取决于知识库质量，不是模型规格**；需政策法规库 + 部门业务库 |
| 公文写作与审核 | 14B–70B，2–4 卡 ≥48GB | 35B-A3B Thinking 模式 + 公文范本 RAG + 格式校验规则 | 公文有严格格式规范（GB/T 9704），需模板引擎兜底；审核需可追溯的修改理由 |
| 多模态政务文档处理 | 122B 起，4–8 卡 | 35B-A3B 原生视觉 + MinerU 版面解析流水线 | 存量红头文件/扫描件/表格/印章识别；**本报告自身就是 MinerU 解析产物** |
| 数据分析 | 报告未给规格 | 35B-A3B + Text2SQL + 只读库账号 + 结果二次校验 | **需打通政务数据库，涉及跨部门数据授权，往往是最慢的一环** |

**从决策链推断出的、报告未明确的场景需求**

- **部门自建智能体的开发支撑**（数据局、纪委、公安、溧投数科都有开发能力）→ 需要开放 API、开发沙箱、独立配额与租户隔离；
- **纪委监委场景**涉密等级最高 → 需独立租户 + 全量审计 + 可能的物理/逻辑隔离；
- **公安局场景**受公安网与政务外网隔离限制 → 大概率无法直连本平台，需单独讨论数据交换方式，**建议在一期范围外**；
- **专家小组的研发与培训需求** → 7 人均为兼职，需要培训、文档与示例工程，否则平台建成后无人会用；
- **12345 热线 / 会议记录**等语音类场景是政务 AI 的高频延伸，建议在需求确认时主动询问。

### 3.5 规模与并发口径（当前最需要向客户澄清的一项）

报告给出的唯一量化目标是"预估总并发会话数可达 50 个以上"，但这个数字**口径不明且与硬件能力严重不符**：

- 一期 8 卡服务器被估为"并发 2–4 个"，二期同样的 8 卡服务器被估为"并发 50 个左右"——**同一硬件，前后差 12–25 倍**，报告内部即不自洽；
- 4 台边缘终端（单台仅 273GB/s 带宽）被估为"并发 16 个"，而 8 卡 L20（合计 6912GB/s，为单台边缘终端的 **25 倍**）却只有 2–4 个并发，**结论与硬件能力方向相反**；
- 经重算（见《03》），单台 8 卡 L20 服务器跑 Qwen3.6-35B-A3B-FP8，**稳态同时生成会话数在 80–150 路量级**，比报告估算高 1–2 个数量级。

**需要与客户对齐的口径**：
1. 全市目标注册用户数（各委办局人员总量）；
2. 日活跃用户数与峰值时段（政务办公有明显的工作日 9–11 点、14–16 点双峰）；
3. "并发"定义——是同时在线、同时发起请求，还是同时流式生成 token；
4. 服务等级目标：首 token 延迟（TTFT）与单用户输出速率（tok/s）的可接受下限。

**经验参考**：政务办公类 AI 应用峰值活跃并发通常为注册用户的 5%–10%。按重算结果反推，**一期单台服务器即可支撑 1500–3000 名注册用户的日常使用**，已远超溧阳市委办局的实际人员规模。这意味着——**本项目的瓶颈从来不是算力，而是场景、知识库与运营**。这是需求分析最重要的一条结论。

### 3.6 合规与安全需求

报告以"数据安全与合规"作为第一论据（引《数据安全法》《个人信息保护法》、等级保护制度），但通篇未落到具体建设内容。方案必须补齐：

| 需求项 | 具体要求 | 报告是否覆盖 |
| --- | --- | --- |
| 等保定级与测评 | 政务 AI 平台通常需等保三级，含测评费与整改周期 | ✗ 未提及，无预算 |
| 内容安全 | 输入输出双向合规过滤，政务场景强制 | ✗ |
| 全链路审计 | 谁、何时、问了什么、模型答了什么、调用了哪些工具/数据，需集中留存（等保要求 ≥6 个月） | ✗ 无集中存储承载 |
| 身份认证 | 对接政务统一身份认证 / OA 单点登录 | ✗ |
| 权限与租户隔离 | 部门级数据隔离，纪委等敏感部门独立 | ✗ |
| 数据脱敏 | 入库与出库两侧的个人信息脱敏 | ✗ |
| 模型与知识来源合规 | 权重来源可溯（Apache 2.0 合规）、知识库文件授权清晰 | 部分 |

### 3.7 预算结构需求（方案阶段必须纠偏）

报告 200 万预算 100% 用于硬件（GPU 服务器 150 万 + 边缘终端 40 万 + 交换机 10 万），**软件与服务费为零**。缺失项：

| 缺失项 | 说明 |
| --- | --- |
| TeleAgent 私有化授权 | 商业软件授权，金额待电信报价，**当前预算无处安放** |
| NVIDIA vGPU 授权 | 若需卡切分（L20 不支持 MIG，只能走 vGPU），需按卡年付费 |
| 实施与调优服务 | 部署、性能调优、模型适配、压测 |
| 知识库与语料建设 | 政策法规、公文范本的清洗、切分、标注——**决定效果上限，工作量常被低估** |
| 场景应用开发 | 4 类场景的落地开发与调试 |
| 共享存储 | NAS 或对象存储 |
| 一期网络 | 交换机被排到二期，一期需现有资源兜底 |
| 机房改造 | 配电扩容、制冷、机柜、UPS |
| 等保测评 | 测评费 + 整改 |
| 3 年维保与备件 | GPU 整机备件 |
| 培训 | 专家小组与各委办局使用培训 |

**建议**：将预算显式拆为"算力基础设施"与"平台及应用"两个科目分列上报。同类政务 AI 项目软硬投资比通常为 6:4 至 5:5。若总额锁定 200 万不变，建议压缩一期硬件（例如边缘终端由 4 台减为 2 台，释放约 8 万），优先保障平台与知识库建设——**否则会出现"算力买齐了但没有可用应用"的局面，这对以"月底见效"为目标的项目是最坏结果**。

## 五、需求分析阶段的核心结论

1. **客户的选型判断整体专业可信**。GPU 四厂商对比逻辑合理（L20 在 MFU、FP8 支持、性价比、生态成熟度上确有优势），模型选型（Qwen3.6-35B-A3B-FP8）经核实完全正确，本地化 vs 云算力的论证扎实。方案应当**支持并强化客户的既有判断，而不是推翻重来**——尤其在硬件已"暂定 L20"的前提下。

2. **报告最大的技术问题是容量测算，且是低估**。这对我们是有利的：可以用重算结果告诉客户"你买的硬件比你以为的能干得多得多"，从而把释放出来的预算与注意力转向真正的瓶颈——平台与知识库。这是一个正向的、易被接受的切入角度。

3. **项目最大的风险不在硬件，在两个第三方节奏**：TeleAgent 私有化包的排期、8 卡 GPU 服务器的到货周期。二者都不由我们控制，因此方案必须设计**双轨交付路径**。（原先担忧的"TeleAgent 昇腾适配与 NVIDIA 路线冲突"因其支持自定义模型提供商而消解，L20 选型得以保留。）

4. **报告的能力缺口集中在"平台与数据"而非"算力"**：无 RAG、无 Embedding/Rerank、无内容安全、无审计、无身份认证、无共享存储、无监控、无知识库建设预算。这些正是方案的价值落点与商务空间。

5. **"月底私有化"的现实解法是降低交付物定义**：将月底目标从"完整平台上线"调整为"最小可用闭环 + 两个真实场景可演示"，在临时或部分硬件上完成，正式硬件到货后平滑迁移。这个预期管理需要尽早与黄黎明副局长沟通。
