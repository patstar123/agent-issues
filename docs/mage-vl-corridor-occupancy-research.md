# Mage-VL 与走廊房间聚集研判：开源 VLM 调研

> 调研日期：2026-08-15  
> 对象模型：[microsoft/Mage-VL](https://modelscope.cn/models/microsoft/Mage-VL)（同步发布于 [Hugging Face](https://huggingface.co/microsoft/Mage-VL)）  
> 论文：[Mage-VL: An Efficient Codec-Native Streaming Multimodal Foundation Model](https://arxiv.org/abs/2607.24904)（2026-07）  
> 代码：[github.com/microsoft/Mage](https://github.com/microsoft/Mage)

本文只做**能力边界与架构选型**评估，不构成可上线执法系统的实施方案。走廊监控属于高风险场景：模型输出不能作为身份认定或处置依据，性别/人数判断在远距、背影、红外、换装条件下误差很大。

---

## 1. 结论先行

**Mage-VL 理论上不能单独满足该需求。**  
它适合作为「走廊实时事件门控 + 短片段语义复核」层，**不能替代**现有的 YOLO + ByteTrack + 人体特征 / ReID + 属性识别，也**不能单独完成**跨进出去重和隔天去重。

更准确的判断是：

| 子需求 | Mage-VL 是否理论满足 | 说明 |
| --- | --- | --- |
| 24h 走廊视频流里发现「有人进出」 | **部分满足** | 原生流式门控 + 运动敏感 token，比均匀抽帧 VLM 更贴实时监控 |
| 一镜监管 15–20 个房门 | **弱** | 远距小人、多门并排，通用 VLM 空间分辨率不够，必须先做门 ROI / 检测 |
| 短时窗内「一女多男」或「超过 5 人」 | **不满足单独使用** | 计数是 VLM 系统性短板；走廊性别识别在背影/低分辨率下不可靠 |
| 同一人反复进出不重复计数 | **不满足** | 没有身份库，也没有跨小时/跨天的身份绑定 |
| 隔天进出不计入本次聚集 | **不满足** | 流式记忆只是近期滑窗，不是跨会话状态机 |
| 替代现有检测跟踪管线 | **不满足** | 指代跟踪 J&F 仍很低；VLM 用类别线索，不用身份向量 |

**推荐方向：** 继续以检测 + 跟踪 + ReID + 房间状态机做主路径；VLM 只做事件触发和歧义片段复核。若要试 VLM，优先组合是：

1. **主路径稳定化**：门线进出计数 + 外观 ReID 库 + 按房间/按自然日的占用状态机  
2. **流式门控**：Mage-VL 或 MiniCPM-o 4.5，只在「某扇门附近出现进出」时唤醒  
3. **短片段复核**：Qwen3-VL（中文生态、定位）或 Molmo2 / Molmo2-VideoPoint（指向、计数、跟踪更强）

单独把 Mage-VL 换成更大的通用 VLM，**解决不了**你现在最痛的「重复进出 / 隔天 / 同一人」问题。

## 2. 需求拆解

场景可以拆成 6 个独立技术问题。它们对模型的要求完全不同：

1. **空间绑定**：画面里 15–20 个房门，每次进出必须落到「哪一间房」。  
2. **事件检测**：谁在何时进入 / 离开某扇门。  
3. **短时占用估计**：某房间在一个连续时段内，当前仍在房内的独立人数。  
4. **属性估计**：独立个体的外观性别（一女多男）。  
5. **身份去重**：同一人短时反复进出只计 1 次。  
6. **跨日重置**：隔天的进出不并入本次聚集。

其中 5、6 本质是**带生命周期的身份状态机**，不是「看一段视频然后回答问题」。  
3、4 在走廊广角下是**小目标 + 背影 + 遮挡**问题。  
1、2 更适合几何标定 + 检测跟踪，而不是端到端 VLM。

现有管线（YOLO + ByteTrack + 特征 + 属性）不稳定，通常来自这些根因，而不是「模型不够通用」：

- 一镜多门，目标很小，漏检/误检会直接污染后续所有模块  
- ByteTrack 在遮挡、交叉、进门消失后再出现时 ID switch  
- ReID 对换装、背包、夜视、侧脸/背影脆弱  
- 属性模型把「长发/裙子」当成性别，走廊里误报高  
- 缺少「按房间、按自然日、按在房状态」的显式账本，模型层再强也会重复计数

VLM 不能自动消掉这些根因。近期论文反而说明：Video-LLM 经常用性别/衣服颜色这类**类别线索**，而不是把视觉身份绑定到某个具体人（见第 5 节）。

## 3. Mage-VL 是什么

### 3.1 定位

Mage-VL 是微软 2026-07 发布的 **4B 编解码器原生、主动流式**多模态模型，目标不是「更会做题」，而是解决作者所说的现代 Moravec 悖论：通用 VLM 离线推理强，但**实时流式感知又慢又贵**。

单权重同时覆盖：

- 静态图像理解  
- 均匀抽帧视频  
- 传统 H.264 / HEVC 码流  
- 神经编码 DCVC-RT  
- 事件门控的主动流式解说

许可证：**Apache-2.0**（独立视觉编码器 Mage-ViT 为 MIT）。国内可从 ModelScope `microsoft/Mage-VL` 拉取；官方推理与门控脚本在 GitHub `microsoft/Mage`。

### 3.2 架构要点

- **Mage-ViT**：从零训练的 Codec-ViT。按 I 帧（锚帧，保留全部 patch）和 P 帧（只保留运动向量 / 残差能量高的 patch）分配 token，`16×16` 网格 + 3D RoPE。视觉 token 可比均匀抽帧少 **75% 以上**，论文称墙钟推理最高约 **3.5×**。  
- **语言模型**：Qwen3-4B-Instruct-2507，经两层 MLP 投影。这是唯一复用的预训练组件。  
- **System 1 / System 2**：轻量认知门控看滚动码流窗口，日常内容保持沉默；只有 `p_speak ≥ τ` 才唤醒完整解码器。门控在 SoccerNet 流式协议上评测，**不是监控事件数据上训的**。  
- **流式记忆**：门控看累积 streaming memory；真正生成时只用**最近若干 codec 片段的滑窗**。可以中途插入文本问题。这不是跨小时、跨天的身份记忆。

训练是五阶段监督课程，**没有**大规模 RL / preference 后训练。作者自己承认：复杂 agent 任务上仍落后 Qwen3-VL，原因包括算力、缺少图文混合预训练、缺少 RL。

### 3.3 和本场景相关的公开分数

同一 4B Qwen3 骨架下，Mage-VL 相对 Qwen3-VL-4B：

| 能力 | 指标 | Mage-VL-4B | Qwen3-VL-4B | 含义 |
| --- | --- | --- | --- | --- |
| 视频问答 | VideoMME | 64.0 | 59.7 | 通用视频理解更好 |
| 长视频 | MLVU-dev / LVBench | 68.7 / 41.8 | 61.5 / 39.2 | 长程事件更好 |
| 时序定位 | Timelens-QVHighlight | 57.4 | 34.9 | 「什么时候发生了什么」更强 |
| 空间推理 | VSI-Bench | 64.3 | 53.3 | 空间关系更好 |
| 在线视频 | OVO-Bench Overall | 64.00 | 63.00 | 在线感知略强，且实时子项更高 |
| 指代跟踪 | Ref-DAVIS17 J&F | 25.83 | 7.48 | 相对更好，**绝对仍然很低** |
| 指代跟踪 | MeViS / Ref-YT-VOS | 22.55 / 25.57 | 3.16 / 5.28 | 同上 |
| 流式触发 | SoccerNet TimVal / F1 | 55.54 / 16.35 | — | 门控能「该说话时说话」，但不是进出事件标签 |

对走廊场景，这些数字应读成：

- **时序定位、运动感知、流式门控**是 Mage-VL 的真长处。  
- **跟踪数字是指代分割（RVOS），不是行人 ReID**。J&F 20–26 不能支撑「同一人反复进出只计一次」。  
- 门控训练分布是体育解说，零样本迁到「12 号房有人进门」需要微调，不能默认可用。

## 4. 逐条对照：理论是否满足

### 4.1 实时走廊流：相对匹配，但不能当检测器

Mage-VL 的设计假设和走廊监控有重叠：码流连续、大部分时间无事、只有少数时刻值得响应。I/P 稀疏编码会优先保留运动区域，人走过门的片段 theoretically 比静止墙面更容易进模型。

限制：

- 门控阈值、段长（官方示例约 8 秒）是为解说设计的，不是为「进门 1–2 秒」设计的。  
- P 帧丢静态 patch：如果人已经站在门口不动，或红外噪声被当成运动，门控会漏或误触发。  
- 4B 全量解码仍不便宜。24h × 多路相机必须「门控沉默、只在事件片段跑 System 2」，否则算力不可持续。  
- 一镜 15–20 门时，远处行人可能只有几十像素。通用 VLM 的 patch 网格对这种小目标不友好。

**理论用法：** 把 Mage-VL 当「这 8 秒里某扇门附近是否发生进出」的触发器，而不是当人数账本。

### 4.2 一镜多房间：必须外挂几何，不能靠模型自己认门

VLM 可以按提示说「左边第三扇门有人」，但：

- 门牌、门框、相似装修会让模型串房  
- 没有标定就没有稳定的 `room_id`  
- 论文空间基准（CV-Bench、VSI-Bench）是室内/具身问答，不是 20 个近似重复的门洞

**必要外挂：** 每路相机标定门 ROI 或门线；检测框与 ROI 求交后再交给后续模块。这一步与用不用 VLM 无关。

### 4.3 「一女多男」或「超过 5 人」：不能单独交给 VLM

这是本需求里最容易被 VLM demo 误导的部分。

**计数。** GroundCount（2026）指出：即便现代推理型 VLM，计数仍是准确率最低的任务之一（约 64%–75%），而检测器做同类计数几乎是平凡的。Molmo2 是开源里视频计数/指向最强的一档，其 VideoCount 准确率仍只有约 **35%–37%**，作者也写明「还没有模型达到 40%」。Mage-VL 论文附录里，即便做了 Zero-Vision RL，PixmoCount 也只有约 **42%**。  
走廊远距、遮挡、半开门，只会更差。要判「是否 ≥5」，应用检测框计数 + 在房状态机，而不是让 VLM 直接报一个数字。

**性别。** 通用 VLM 能做粗外观描述，但走廊里常见背影、帽子、宽松衣服、夜视、低分辨率。这不是「换一个更大 VLM」能稳定过关的问题。属性识别专用模型（如 SOLIDER-PAR，PA-100K mA 约 84–86）仍然是更合适的感知头；即便如此，也应输出概率，并允许「未知」。  
「一女多男」在工程上应写成：`n_female_est ≥ 1 且 n_male_est ≥ 2 且 n_unique ≥ 3`，并且带置信度和人工复核，而不是一句自然语言判定。

### 4.4 同一人去重、隔天重置：VLM 结构上做不到

这是 Mage-VL（以及几乎所有通用 Video-LLM）的硬缺口。

- 没有外观特征向量画廊，没有 `person_id`。  
- 流式记忆是近期滑窗，重启进程、换班、隔夜都会丢。  
- 「隔天不计入」是业务规则（按自然日或入住单截断），应写在状态机里，不该指望模型「看懂是不是昨天那个人」。  
- 指代跟踪分数低，说明连「这段视频里指定的那个物体」都做不稳，更谈不上跨小时重识别。

2026 年的诊断研究（长视频角色跟踪、TOC-Bench）结论一致：Video-LLM 的高分常常来自类别捷径，**没有把视觉身份绑定到具体个体**；对遮挡、消失再出现、身份敏感计数仍然远低于人。

因此：

- 「同一人进出三次只计 1」→ 必须是 ReID 特征 + 时间衰减画廊 + 在房集合。  
- 「隔天不算」→ 必须是按 `room_id + calendar_date`（或订单时段）清空占用集。

Mage-VL 最多能在短片段里说「好像是刚才那件红衣服」，这不能当去重主键。

### 4.5 对现有不稳定性：VLM 不是替换，是复核

你现在的不稳定，多半出在小目标检测、ID switch、ReID 域差、属性误报、缺少房间账本。换 VLM 端到端，等于把这些问题藏进黑盒，还失去框级审计。

VLM 真正可能帮上忙的位置只有三个：

1. **事件门控**：减少全时段重推理。  
2. **歧义片段复核**：检测器说「5 人进门」，VLM 看 8–16 秒裁剪后回答是否像聚集、是否像清洁/搬家/送货。  
3. **人工核查辅助**：给值班员一段自然语言摘要 + 关键帧，而不是自动立案。

## 5. 同类开源模型怎么选

按「和本场景的接口」分组，而不是按榜单总分。

### 5.1 流式 / 在线视频（和 Mage-VL 同型）

| 模型 | 规模 | 和本场景的关系 | 许可 / 获取 |
| --- | --- | --- | --- |
| **Mage-VL** | 4B | 目前最贴「码流进、事件出门控」的开源方案；跟踪/计数弱 | Apache-2.0；HF / ModelScope `microsoft/Mage-VL` |
| **MiniCPM-o 4.5** | ~9B | 全双工音视频流，端侧/边侧友好；适合实时看+说，不是 ReID | 见 OpenBMB 发布页；国内生态较好 |
| **Qwen3-Omni** | MoE（如 30B-A3B） | 原生音视频流式；部署重，适合中心推理，不适合一路一卡硬上 | Apache-2.0；ModelScope 齐全 |
| StreamForest / HERMES / TimeChat-Online / VideoLLM-online | 7B 级 | Mage-VL 论文里的在线基线；OVO-Bench 上整体低于 Mage-VL-4B | 研究向，工程成熟度一般 |

若调研目标就是「VLM 能不能做实时走廊感知」，**Mage-VL 是这类里最值得先跑通的**。它不是计数/去重最优。

### 5.2 通用视频理解 + 中文落地（更适合做复核层）

| 模型 | 规模 | 和本场景的关系 | 许可 / 获取 |
| --- | --- | --- | --- |
| **Qwen3-VL** | 4B / 8B / 32B / MoE | 中文、文档、2D/3D grounding、长视频（256K–1M）最完整；vLLM / SGLang 成熟。静态和 agent 强于 Mage-VL，流式效率弱于 Mage-VL | Apache-2.0；ModelScope 官方合集 |
| **InternVL3.5** | 1B–241B | 规格全，推理强化明显；适合已有 InternVL 栈的团队 | 开源权重；国内常用 |
| **GLM-4.1V-9B-Thinking / GLM-4.5V** | 9B 级 | 中英双语、思维链复核；延迟高于 Instruct 模型 | 智谱开源；ModelScope 有 |
| **MiniCPM-V 4.5** | 8.7B | 视频理解效率高（官方 Video-MME 推理时间远低于同级 thinking 模型），边侧部署友好 | OpenBMB |
| **Keye-VL 1.5** | 8B | 中等通用 VLM，生态小于 Qwen / InternVL | 开源 |

**复核层首选 Qwen3-VL-8B 或 32B**：能对门 ROI 裁剪做中文结构化输出（房间、进出方向、粗人数、粗属性、是否像送货/清洁），并给出框/时间定位。不要用它做跨天身份。

### 5.3 计数 / 指向 / 视频跟踪更强（仍不是 ReID）

| 模型 | 规模 | 和本场景的关系 |
| --- | --- | --- |
| **Molmo2-4B / 8B** | 4B / 8B | 开源里视频指向、计数、跟踪最强一档。VideoCount Acc 约 34–36%；视频跟踪 J&F 论文称可到约 56，并超过部分闭源模型。适合「把人点出来」而不是「报一个数」 |
| **Molmo2-VideoPoint-4B** | 4B | 只为视频指向/计数微调，VideoCount Acc 约 36.8 / Close Acc 约 56.5。若只做短片段「点出每个人再计数」，比通用 Mage-VL 更对口 |
| Mage-VL 指代跟踪 | 4B | Ref-DAVIS17 J&F 25.83，相对 Qwen3-VL-4B 高，但远低于 Molmo2 的跟踪档 |

注意：Molmo2 的「跟踪」是点/掩膜级视频目标跟踪，**仍然不是跨相机、跨天行人 ReID**。它能帮助减少「数错人」，不能建立身份库。中文指令和国内部署生态弱于 Qwen。

### 5.4 不该用 VLM 替换的专用模型

这些才是 5、6 两类需求的正解：

| 任务 | 更合适的开源方向 | 代表 |
| --- | --- | --- |
| 行人检测 | 小目标检测，而不是 VLM | YOLO11 / RT-DETR，门 ROI 内推理 |
| 短时跟踪 | 多目标跟踪 | ByteTrack / Bot-SORT；重点治 ID switch |
| 跨进出、跨小时身份 | 外观 ReID 画廊 | [SOLIDER-ReID](https://github.com/tinyvision/SOLIDER-REID)、[TransReID](https://github.com/damo-cv/TransReID)、CLIP-ReID、OSNet。Market1501 上 SOLIDER 可到 90+ mAP，走廊域必须现场微调 |
| 性别/衣着等属性 | 行人属性识别 | [SOLIDER-PAR](https://github.com/tinyvision/SOLIDER-PersonAttributeRecognition)（PA-100K mA 约 86） |
| 进出计数 | 门线 / 区域占用 | 检测框与门线求交，维护 `in_room` 集合 |
| 隔天重置 | 业务状态机 | `room_id + date` 或入住单时段清空 |

VLM 做 text-to-image ReID（如 Auto-ReID 一类工作）可以当检索辅助，不能替代特征向量画廊。

## 6. 建议架构（混合，而不是换模型）

```
相机码流
  ├─ 门 ROI / 门线标定（每路一次）
  ├─ 行人检测（YOLO / RT-DETR，只在门附近）
  ├─ 短时跟踪（ByteTrack / Bot-SORT）
  ├─ 外观特征 → ReID 画廊（按房间、按自然日分片）
  ├─ 属性头（性别等，输出概率，允许未知）
  ├─ 房间占用状态机
  │     enter: 特征匹配已有 ID 则复用，否则新建
  │     exit:  从 in_room 移除，特征保留到日终
  │     日切 / 订单结束: 清空该房间占用，特征可归档不参与计数
  │     告警: |in_room|≥5  或  (n_f≥1 ∧ n_m≥2 ∧ |in_room|≥3)
  └─ VLM 只在状态机翻转或低置信时启动
        Mage-VL / MiniCPM-o: 要不要看这段
        Qwen3-VL 或 Molmo2-VideoPoint: 这段裁剪里有几个人、是否像聚集
        结果只写复核字段，不覆盖状态机主键
```

三层职责必须分开：

1. **账本层**（检测、跟踪、ReID、日期）：唯一能保证「不重复计数」的地方。  
2. **门控层**（Mage-VL 一类）：省算力。  
3. **语义复核层**（Qwen3-VL / Molmo2）：降误报，给人工看。

---

## 7. 若仍要验证 Mage-VL，建议怎么测

不要先上全走廊 24h，先做离线切片对照。每条都要有检测器基线，否则无法判断 VLM 是增益还是噪声。

1. **门事件召回**：人工标 200 段「进/出/路过/停留」，比 Mage-VL 门控 vs 检测+门线。看漏报（人进门但门控沉默）和空报（无人但说话）。  
2. **小目标**：把 15–20 门按近/中/远三档拆开。若远门明显崩，说明必须先裁 ROI，不能整帧喂 VLM。  
3. **计数对照**：同一段裁剪，比较 YOLO 去重人数、Mage-VL 口头人数、Molmo2-VideoPoint 点数。重点看「是否 ≥5」的二分类，而不是绝对人数。  
4. **属性对照**：只评估正脸/侧面可辨样本；背影应允许「未知」。和 SOLIDER-PAR 对比，而不是只看 VLM。  
5. **去重对照**：构造「同一人 10 分钟内进出 3 次」和「隔日同一人再来」。VLM 单独跑预期会失败；用来确认必须外挂 ReID + 日切。  
6. **算力**：一路 1080p，门控沉默占比、触发后 4B 解码延迟、能否和现有检测共用一张卡。

通过标准应当是：**门控降低无效推理，复核降低明显误报；人数和身份仍以状态机为准。**  
如果门控召回低于检测+门线，Mage-VL 就只保留离线抽检，不要进实时链路。

---

## 8. 选型建议（按优先级）

1. **先不要换掉现有感知栈。** 优先做门 ROI、进出线、按房间按日的占用集合、ReID 画廊分片。这直接对应「重复进出 / 隔天」。  
2. **要试流式 VLM，选 Mage-VL。** 它和「一路相机长期盯走廊」的计算形态最像；4B、Apache-2.0、HF/ModelScope 都有。预期收益是事件触发，不是精确计数。  
3. **要试语义复核，选 Qwen3-VL-8B/32B。** 中文、定位、工程栈都更稳；和 Mage-VL 论文也是同一量级对照。  
4. **要试「把人点出来再数」，选 Molmo2-VideoPoint-4B。** 这是开源 VLM 里和「≥5 人」最接近的能力，但准确率仍远不够单独告警。  
5. **边侧实时看+说，选 MiniCPM-o 4.5 / MiniCPM-V 4.5。** 比 Mage-VL 更偏端侧产品，同样不解决 ReID。  
6. **不要指望任何通用 VLM 给出可执法的「一女多男」结论。** 属性头 + 人工复核是下限。

## 9. 2K 输入能跑多少帧率？

官方**没有**公布「2K 分辨率、每秒处理多少帧」的数字。现有材料只能得到下面这条更准确的结论：

**Mage-VL 默认不会按 2K 原生像素做 ViT 推理。**  
相机可以是 2K/1080p 码流，但送进模型的画面会被压到约 `max_pixels=150000`（约 387×387，不到 2560×1440 的 1/20）。官方在线评测协议是 **1 fps**；流式示例是 **每 8 秒看一段**，frames 后端默认 `cur_fps=2`。它不是 2K@25/30 的实时检测器。

### 9.1 官方实际用的分辨率

| 来源 | 分辨率 / 像素预算 | 含义 |
| --- | --- | --- |
| Mage-ViT 图像预训练 | 224–448 | 没有 2K 训练分布 |
| Mage-ViT 视频预训练 | **256**，64 帧，token 预算 4096 | 主视频分布是低分辨率 |
| 图像表征探到的最高点 | 676 token（约 26×26 patch ≈ 416px） | 可变分辨率只验证到这个量级 |
| 官方 `inference.py` / 流式脚本 | `max_pixels=150000` | 约 15 万像素，不是 2K 的 368 万像素 |
| 码流打分（HEVC bit-cost） | 可读原生码流分辨率 | 只用于选哪些 patch 重要，不代表 ViT 吃 2K |
| DCVC 神经编码 | `max_side=0` 可全分辨率打分，但更慢 | 同样是打分，不是 2K 密集编码 |

2K（按 2560×1440）一帧约 368 万像素。Mage-ViT 的 patch 是 16×16，I 帧还要**整帧保留**：

- 官方预算：约 588 个 patch / I 帧（≈150k 像素）  
- 原生 2K：160×90 = **14400** 个 patch / I 帧，约 **25 倍**  
- 再经 2×2 spatial merge，仍约 3600 个视觉 token / I 帧，远超训练时单帧量级

所以「2K 输入」如果是指**不缩放、整帧进模型**，既不在训练分布里，也会把 4B 解码器的视觉 token 打爆。官方路径是：码流可以是 2K，**canvas 缩到 15 万像素再推理**。

### 9.2 官方实际用的帧率

| 模式 | 官方设置 | 这不是什么 |
| --- | --- | --- |
| 短视频预训练 | **1 fps**，最多 30 帧 | 不是摄像机 25/30 fps |
| 在线评测 OVO-Bench | **1 fps**，只用最近 4 帧 | 论文里的「实时感知」协议 |
| 流式脚本 `inference_streaming.py` | `segment_sec=8`，frames 时 `cur_fps=2` | 每 8 秒一个窗口，不是逐帧生成 |
| 离线 codec 默认 | `target_canvas=32`（tc32） | 画布预算约等于 32 帧均匀采样，不是 32 fps |
| 轻量档 tc8 / tc16 | 约等于 8 / 16 帧均匀采样的视觉预算 | 用更少 token 换速度 |

论文写的 **最高 3.5× 墙钟加速**，是相对「同一个 Mage-VL 做均匀抽帧」，测在 **8×B200** 上整集评测（例如 NExT-QA tc8 用 415s 对 Qwen3-VL-4B 的 1460s）。这不是单卡 2K 实时 fps。

### 9.3 走廊场景里可以怎么理解

- **相机 2K、模型 1–2 fps 等效观察**：符合官方设定。门控看 8 秒码流窗口，日常沉默，进出时再跑 4B 生成。  
- **相机 2K、模型按 25/30 fps 逐帧理解**：官方不支持，也没有这个数字。I 帧全保留会让计算随分辨率平方涨。  
- **远门小目标**：先缩到 15 万像素，15–20 个门里远处的人会更糊。要保 2K 细节，应先裁门 ROI，再把 ROI 送到 `max_pixels` 预算里，而不是整帧 2K 硬喂。  
- **单卡消费级 GPU**：论文没有 A100/4090 数字。工程上应默认「门控 1–2 Hz 看一次，触发后再生成」，不要按 25 fps 规划 VLM 算力。

一句话：**2K 只能当码流分辨率；Mage-VL 吃的是约 400px、1–2 fps（或每 8 秒一段）的稀疏窗口。**
